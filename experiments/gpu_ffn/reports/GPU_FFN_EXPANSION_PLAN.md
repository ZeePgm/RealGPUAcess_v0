# Qwen3-0.6B 全 FFN 权重递进实验方案

日期：2026-11-04。状态：[F1](GPU_F1_RESULTS.md)、[F2](GPU_F2_RESULTS.md) 均已实现并实际运行通过；[F3](GPU_F3_RESULTS.md) 已完成全量运行并通过验证，三级实验全部完成。

目标是在保持原生 GPU KV 的条件下，将 HBF 权重访问覆盖从单层完整 FFN 扩大至全部 28 层 FFN。采用三级联合实验，共用一次 native 参考和一份计算时间表；不重新执行整套 S0—S9。

## 1. 范围与固定条件

- 模型：原 S 系列同一份 Qwen3-0.6B F16 GGUF，以实际模型哈希和元数据确认身份。矩阵为 F16；不转换或修改模型中的其他数据类型。
- 本轮仅接入 `blk.L.ffn_gate.weight`、`blk.L.ffn_up.weight`、`blk.L.ffn_down.weight`。28 层共 84 个矩阵，每个 1024×3072×2 B = 6 MiB，总量 504 MiB。
- FFN norm、attention、embedding、输出层不计入本轮 HBF 选区；它们仍参与真实 GPU 推理。KV 保持原生 GPU 路径。
- 单请求、单序列、greedy；沿用原 44-token prompt，最多 8 个非 EOS 输出。context/batch/ubatch = 512/256/256，原生 F16 KV、MUL_MAT 显式 F32，关闭 CUDA graphs 与 flash attention。
- GPU 完整执行模型；选中的权重消费者在 HBF 父访问及其子请求成功后才执行。权重真实字节仍在 GPU，HBF 保存符号内容身份并计算行为与时序。
- 访问合同：一次实际矩阵消费者调用，对所登记完整矩阵提交一次父读。prefill 不按 prompt token 数额外乘流量；先从 native 事件核验消费者次数，再确定期望工作量。

## 2. 三级实验与运行次数

层号从 0 开始。三个选区逐级包含前一级。

| 阶段 | HBF 覆盖 | 矩阵数 | 登记有效量 | 8 步累计有效读 | 目的 |
|---|---|---:|---:|---:|---|
| F1 | 第 10 层的 gate/up/down | 3 | 18 MiB | 144 MiB | 验证完整矩阵、多算子接入，并测量软件成本 |
| F2 | 第 0、10、20、27 层的 gate/up/down | 12 | 72 MiB | 576 MiB | 检查跨层映射、首末层覆盖和随规模增长的资源消耗 |
| F3 | 第 0—27 层的 gate/up/down | 84 | 504 MiB | 4032 MiB（3.9375 GiB） | 完成全 FFN 覆盖，汇总对 token 模拟时间的影响 |

核心批次共四次 GPU 推理：native 一次，F1/F2/F3 各一次。另有一次不执行 GPU 推理的清单及配置预检。初始化与必要预热单列，不计入四次请求或 token 延迟。

各级通过后进入下一级；失败时在本级定位，不把失败样本混入成功结果。无需为每一级重复生成 CPU 参考、重新采样多份 GPU 时间表或制作独立报告。若 native 或联合执行提前 EOS，按实际输出和消费者调用重新计算规模；输出不足两枚时 TPOT 不适用。

## 3. 统一后端配置

三级始终使用同一份 512 MiB 配置。8 MiB 是旧小实验的容量选择，本轮按全 FFN 工作集重新配置。通过增加 block 数扩容，保持通道数和 bank 并行结构不变。

```ini
[device.geometry]
host_channels = 1
dies_per_channel = 1
banks_per_die = 2
pages_per_block = 16
blocks_per_bank = 4096
spare_blocks_per_bank = 1

[host]
max_resident_fragments = 256
max_logical_fragments = 1000000000

[run]
total_events = 0
events_per_tick = 100000
rounds_per_tick = 100000
max_tick_ps = none
```

这是对旧 H0 的参数替换片段，不是一份独立完整 INI。其他字段从原有效配置继承：MOCS=256、max_pending_write_dlus=4、Global chunk=4096 B、64 B 片段、Host/NAND FCFS、原介质与链路时延、原缓冲配置。实际运行保存 resolver 导出的完整有效 INI。

容量计算：1×1×2×16×4096×4096 B = 512 MiB。全部 FFN 占 504 MiB，剩余 8 MiB。每个 6 MiB 矩阵已对齐 4 KiB，无额外尾填充；最终仍以实际 GGUF 清单核验。

`max_logical_fragments` 是累计输入保护，`max_resident_fragments` 是活动预算，二者不可混用。`total_events=0` 在当前事件队列中表示不设累计事件上限，用于解除旧 1000 万事件截断；不改变后端服务能力。执行器仍记录运行状态、耗时和资源占用，并允许外部中止；本方案未承诺无限资源。

地址先按全部 84 个矩阵建立唯一布局，顺序为 layer、gate/up/down，逐矩阵连续排列。F1/F2 从该布局中选择，保留与 F3 相同的 Global 地址。每例新 Session，只通过普通写初始化该级实际登记区域，不初始化整个 512 MiB，也不把初始化写计入请求读流量或 token 延迟。

## 4. 一份计算轨迹与配对方法

在同一批次执行一次 native 参考：HBF 访问关闭，保留原生 KV 和与联合实验相同的算子、精度与同步边界。记录完整 logits、输出 token、消费者序列及 GPU 活动时间，生成一份固定计算时间表。

单次轨迹用于该请求的固定轨迹机制比较，不用于估计 GPU 时间分布或代表生产推理性能。若能先证明已有 S6 表与新入口的模型、输入、执行边界和事件序列完全匹配，可复用该表；本方案默认新批次一次采集，不依赖旧输出目录齐全。

从固定表生成零等待 G2 token 时间，不额外运行 GPU。F1/F2/F3 的 G3 都执行真实 GPU 节点和真实 HBF 后端访问，按同表推进模拟计算；当次 GPU 墙钟和后端软件运行耗时不加入模型时钟。

增加选区不得改变 CUDA 算法或表边界。逐段核对 ID、类型、执行步和消费者顺序；不匹配即停止，不能按张量名猜配。联合运行保留段匹配和同步门控证据；精简记录不宣称做过完整 CUPTI/API 时间线审计。

## 5. 规模与软件资源管理

以下是假设每个登记矩阵在 8 个计算步骤各出现一次消费者、无 EOS 提前结束时的独立期望值。

| 阶段 | 父读数 | 4 KiB 读 Global 数 | 64 B 读片段数 | 初始化写与读合计逻辑片段数 |
|---|---:|---:|---:|---:|
| F1 | 24 | 36,864 | 2,359,296 | 2,654,208 |
| F2 | 96 | 147,456 | 9,437,184 | 10,616,832 |
| F3 | 672 | 1,032,192 | 66,060,288 | 74,317,824 |

这些计数不是 NAND sense 次数、链路字节数或事件总数。后端的缓存、合并、分派和初始化状态会影响内部行为；不假设时延随选区容量严格线性或单调。

运行前必须实现适合该规模的记录方式：不附加保留全部片段/attempt 的 StatisticsCollector；使用在线汇总与有界诊断，父访问与逐 token 结果保留。仅停止写 JSON 而继续在内存积累明细不算轻量化。

独立审计由输入清单和消费者事件生成期望，使用区间或按 Global 建索引的方法；禁止每个 Global 再扫描整个 logical_work 列表。对片段覆盖可在线核对顺序、地址、计数和成功归属，无需为每个片段构造 Python 字典。

即使关闭统计明细，后端已完成 Global 与版本历史仍可能随累计输入增长，因此记录峰值 RSS，不能把活动预算 256 当作内存总量上限。

F1 分别测量初始化、GPU 请求中的后端调用、记录/审计、整个进程耗时和峰值 RSS。结合实际 Global、片段、事件处理量估算 F2/F3，再用 F2 实测修正 F3 预算。此前小选区的 18—23 秒进程耗时不作为全 FFN 的直接预测；本方案不编造分钟级完成承诺。

## 6. 每一级的通过条件

1. 覆盖正确：登记集合、消费者次数、地址区间、有效字节、父读与子 Global 数均与独立期望一致；非 FFN 和非选层不产生 HBF 权重读。84 个矩阵的身份和完整范围在 F3 全部覆盖。
2. 数值不变：输出 token、结束原因及完整 logits 与本批次 native 逐位一致，且 logits 有限。本轮仅增加同步依赖，不改变矩阵算法；不通过放宽阈值掩盖差异。
3. 依赖正确：选中消费者提交前已有成功依赖；任何依赖失败阻止消费者继续。全部登记 Global 最终完成，无失败、遗漏或重复归属；成功结束时 Host/Device 排空。
4. 时间一致：对每个交付 token，G3 相对时刻减 G2 相对时刻等于该 token 前累计 HBF 等待，整数 ps 残差为零。初始化、模型加载、验证拷贝和关闭成本单列。
5. 执行匹配：计算表完全消费，边界和调用序列与 native 一致；没有多算最后一个无用预测步骤。实际 EOS 作为独立结束事件处理。

性能效果不设“必须达到多少延迟增量”的通过门槛；本轮首先验证扩大覆盖后的访问、数值和模拟时间记账。单次运行不报告置信区间、稳定吞吐或可靠 p99。

## 7. 保留文件与最终交付

共同文件：模型与构建哈希、prompt/token IDs、完整有效配置、84 矩阵布局、三个子集清单、native logits/token、固定计算表及哈希。

每级文件：实际配置与清单引用、逐矩阵调用和字节汇总、逐父访问完成/成功/等待记录、逐 token G2/G3 配对表、完整 logits/token、阶段计数、时间守恒、后端结束状态、门控与段匹配检查、软件耗时和峰值 RSS。失败时保留原因及有界诊断；不导出全量 GPU 中间数组或逐片段 JSON。

最终只交付一份总报告及三组对照：覆盖规模与模拟 TTFT/TPOT、逐 token HBF 等待、软件耗时/峰值内存随规模的变化。报告明确区分模拟延迟与软件墙钟。

完成后可表述为：在本模型、本输入、原生 KV、指定 HBF 参数和同步门控方式下，全部 FFN 权重消费者均接入后端且通过上述核验。该结果不等同于全部模型权重接入、实际权重卸载或真实 HBF 硬件性能预测。

## 8. 实现范围

现有 S8 入口固定读取 M2 清单，并依赖旧输出路径及固定段数；现有 gate 附加全量统计收集器，旧审计存在反复扫描明细的实现。正式运行前，需要新增可配置实验入口，完成实际 GGUF 清单生成、三级子集选择、512 MiB 配置导出、新批次 native 表生成及校验、汇总统计与独立覆盖审计。

F1 所需新入口、实际 GGUF 清单、512 MiB 配置、新批次 native 表生成、在线统计及独立覆盖审计已实现并验收，见 [运行入口](../README.md)。入口已扩展到 F2/F3，支持校验并复用 F1 的 native 记录和计算表；F2/F3 均已实际运行通过；三阶段对照见 [F3 总报告](GPU_F3_RESULTS.md)。F3 使用原 512 MiB 配置、同一 GPU 二进制及运行 DLL，软件进程超时显式设为 21600 秒。旧 S/A 批次及其结论保持原样。
