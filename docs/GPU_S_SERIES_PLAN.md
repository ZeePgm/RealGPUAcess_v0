## 1. 递进关系与公共条件

| 步骤 | 本步新增的复杂度 | 实验条件摘要 | 必须交付的核心结果 |
|---|---|---|---|
| S0 | 环境和配置准备 | 不运行正式推理；锁定输入、版本、后端候选配置 | 输入/环境清单、配置检查与阻断项 |
| S1 | 无 GPU 的时间与映射合同 | 合成事件；先替身计时，再真实桥接访问 | 35μs/12μs公式验收、独立映射与异常审计 |
| S2 | 真实 GPU，但不加 HBF 等待 | 原生 KV；短 prompt；输出上限1和2；独立校准输入 | 原生事件基线、访问语义、CPU精度合同 |
| S3 | 单区域接入 | 同一短 prompt；最多1输出；M1；模拟计算为0 | 单区域三方数值、覆盖、等待与排空结果 |
| S4 | 从单区域扩大到多区域 | 保持最多1输出和零计算，只把M1扩为M2 | 双tensor交集、父子归属、填充与覆盖结果 |
| S5 | 从1输出扩大到多输出 | M2；上限先2后8；零计算及固定段时间 | 多token三方数值、边界与时间守恒结果 |
| S6 | 用实测取代固定计算输入 | S5冻结的最多8输出案例；native测量；HBF关闭 | G1原始样本、采样评估、完整计算表 |
| S7 | 建立同口径零等待对照 | 只回放S6表和事件；不需要GPU；HBF等待为0 | G2逐token时刻与计算分解 |
| S8 | 加入真实HBF依赖等待 | 同表/同事件/M2；真实CUDA经同步桥门控 | G3逐token时刻、G2/G3差值、数值与排空 |
| S9 | 汇总可审查结论 | 只分析已通过的S6/S7/S8数据 | 三张主图、覆盖/误差/状态表及复现索引 |
| S10 可选 | 覆盖或介质参数敏感性 | 基于S8，每次只改变一个因素 | 配对敏感性结果及适用范围 |

主依赖链是 `S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8 → S9`。S1验证计时和映射工具，S2建立数值与访问依据，S3—S5验证联合执行功能，S6—S8才形成实测计算驱动的正式模型结果。前几步的人工计算时间不进入最终性能主图。

### 公共条件 K

以下条件在各步骤引用“K”时继承；步骤明确列出的变化除外。

| 项目 | 条件 |
|---|---|
| 版本 | 当前llama.cpp、增量后端及已记录overlay；每次运行记录实际源码/补丁和二进制身份 |
| 主模型 | Qwen3-0.6B，实际F16 GGUF、F32 norm、F16 KV；形状及转换哈希通过现有能力检查 |
| 主输入P | `adapters/llama_cpp/prompt.txt` 的固定UTF-8内容和实际token IDs；沿用已声明分词规则，不隐式套模板 |
| 运行 | 单请求、单序列、单可见GPU、greedy；EOS独立记录，不算用户输出 |
| GPU路径 | 原生F16 KV；固定算子、精度与线程设置；graphs/flash attention关闭；同步门控边界不重叠 |
| 容量设置 | n_ctx=512、n_batch=256、n_ubatch=256仅为候选；S2按访问语义确认后锁定。检查P和生成长度符合实际容量 |
| 后端H0 | 采用总体方案第4节配置，经resolver和前进性检查后锁定；单channel、FCFS、chunk=4096B、resident=256；介质/链路参数不变 |
| 初始化 | 每次HBF正向案例使用新Session，经普通Global写完整初始化；初始化成功后设置请求t0；加载/初始化/最终排空另计 |
| 数据位置 | 权重真实字节保留GPU；HBF保存符号内容；KV不注册到本轮权重HBF空间 |
| 请求指标 | token ID可交付时刻打点；不包含加载、分词、文本解码与传输；N<2的TPOT=null |

H0不是硬件校准值。物理GPU架构、CUDA/驱动、GPU选择和工具路径由当前环境配置层指定；缺少资源直接阻断。S0只记录初始身份；若后续逐步实施导致源码变化，每一步记录新的身份，不能把旧验证直接归给新二进制。

### 结果与进入规则

每步建立独立且不覆盖旧数据的结果目录，拟用 `output/gpu-s/<study-id>/Sxx/<case-id>/<run-id>/`。每步至少交付：

- `conditions.json`：全部有效条件、与前一步相比的变化、输入/合同/源码/二进制哈希。
- `stage-result.json`：case/run列表、`pass/fail/blocked/inconclusive`、验收逐项结果、实际N和结束原因、产物索引；未取得的数值为null并说明原因。
- 原始事件、必要快照/比较结果、审计结果及简短 `report.md`。具体文件名是C，必须字段不可省略。

只有本步必做案例全部满足进入标准，才能将其输出作为下一步输入。缺资源/合同未定为blocked；运行失败为fail；数据不足以支持目标为inconclusive，不能都记作pass。构建成功和进程返回0不单独构成验收。

**目的与依据：** R原文第6/9节要求来源、哈希和可复现配置；L先排除输入/环境差异，避免后续误判。

**条件与操作：**

1. 检查K中的GPU、工具链、模型、conversion、profile和主prompt；保存模型实际H/F/层数、P的token IDs及容量检查。
2. 预登记与正式P分离的CPU校准输入，保存文本及token IDs；校准集合需覆盖prefill、decode、所选norm/down和KV追加。缺少覆盖时登记缺项，不用正式性能结果调整容差。
3. 解析H0并核对候选区域的地址容量、64B对齐及完整local DLU初始化条件；此步不产生正式TTFT/TPOT结果。
4. 建立 `study-lock.json`：输入、GPU/工具链、候选配置、固定/可变因素、结果目录、预算；B1访问语义、B2精度合同、采样协议暂标pending，不能填入未经论证的值。

**产出：** `environment.json`、输入哈希/分词清单、`study-lock.json`、`effective-H0.ini`、`preflight.json`及缺项列表。

**进入S1的标准：** 所需输入可获得且校验通过；H0可解析；主案例容量合法。此步仅证明准备就绪，不证明CUDA数值或HBF访问成功。

**已执行结果（新版批次）：** pass。RTX 5070、Qwen3-0.6B F16 GGUF、主prompt 44 tokens；模型/conversion哈希、分词容量、依赖构建身份和H0 resolver检查通过。保存的身份和有效配置见[新版S2结果](GPU_S2_B2_V2_RESULTS.md)及其S0目录。

## 3. S1：先验证时间公式和映射工具

**目的与依据：** R原文第6节明确要求无CUDA的35μs/12μs例子；第3/5/8节要求映射、背压、异常与排空。L将工具错误与GPU错误分开。

**条件与操作：** 不加载GPU模型，不使用实测计算表；分成不同证据等级的案例：

| 子例 | 条件 | 操作及可预先确定的结果 |
|---|---|---|
| S1-a 公式 | 合成计算和等待事件；等待由测试替身给定 | 10+20+5μs产生token1，3+7+2μs产生token2；应得TTFT=35μs、ITL=TPOT=12μs |
| S1-b 真实桥 | 真正TensorAccessBridge/H0；A、B各8KiB，chunk=4KiB；计算间隔0 | 通过桥初始化，再读A两次、B前4KiB一次；有效注册16KiB、触达12KiB、累计读20KiB，3次读父访问、5个读Global最终成功 |
| S1-c 边界 | 分离的测试输入 | N=0/1、EOS标记、零段、首尾段、错序/缺项/重复/哈希错配；验证null和明确拒绝 |
| S1-d 映射/反馈 | 每次单独改一个条件 | 非零偏移、一个回调多交集、别名去重、填充；非法重叠/越界/容量不足拒绝；resident=64的显式子例验证背压后继续 |

S1-a的20/7μs不是H0应产生的延迟；S1-b真实等待值由后端运行得出，不能预填。测试替身结果不作为真实后端或GPU成功证据。

**产出：** `formula-check.json`、`mapping-cases.json`、桥父子/Global日志、`coverage.csv`、`negative-cases.json`。每个真实案例保存实际等待、登记/完成/成功和关闭/排空状态。

## 4. S2：原生GPU基线、访问语义和独立CPU合同

**目的与依据：** R原文第4/6节要求真实执行边界、独立数值参照与回调含义。L先知道GPU实际做了什么，再接HBF。此步完成总体方案B1/B2。

**条件：** K；HBF等待关闭；原生KV；verify模式。主P分别以最多1、最多2个输出执行，前者覆盖prefill/token1，后者覆盖decode。CPU校准使用S0预登记的其他输入；当前旧runner不支持1输出，需要未来实验入口提供，不能把2输出旧入口结果当作1输出。

**操作：**

1. 在实际消费者执行处记录原始回调、源范围、operation/launch、position或position-range；记录request/prefill/token/EOS/end边界。
2. 用实际kernel/stream依赖和源范围独立核对hook；明确每个逻辑访问代表什么、批内复用如何处理、与PTX/warp事件的区别。不按输出行数复制访存。
3. 证明hook位于依赖计算之前，并选定与同步桥及GPU测量相容的边界。需要算子拆分时，native与后续HBF必须采用相同拆分。
4. 在独立校准输入上分析权重转换、精度、KV舍入、归约差异，验证CPU参照并按总体方案第7节冻结 `numerical_contract.json`；再用已冻结判据核对主P的native结果。
5. 冻结 `access_semantics.json`、容量/ubatch设置、完整原始事件schema和候选清单：M1=norm[0,4H)，M2=M1+down[0,2F)。M8及非零偏移范围也需先证明有实际消费者覆盖。

**产出：** 原生token/完整logits、关键hidden/KV比较、`native-events.jsonl`、`boundary-audit.json`、`access_semantics.json`、`numerical_contract.json`及校准依据、冻结后的 `study-lock.json`。

**进入S3的标准：** 独立CPU合同有依据且主P通过；事件含prefill及至少一次decode，token与执行边界关联完整；M1/M2及必做回归范围可独立核对。若提前EOS未覆盖decode，保留结果并使用预登记备用输入补齐覆盖，不屏蔽EOS。访问含义或CPU合同未成立则停止。

**已执行结果（新版分类工程判据）：** pass。新校准g/h各343/343数组通过；主P的1输出172/172、2输出343/343通过，token分别为[32]和[32,6366]。B1消费者/源范围及M1/M2/M8/偏移覆盖、392个有效GPU KV发布数组逐位舍入、verify/timing完整logits一致、无额外预测步和预发射中止fixture通过。新旧执行器主P完整logits、有效快照和事件结构一致。阈值是用户要求采用的分类工程预算，非已证明的全网络误差界；本步无HBF请求。详细判据、条件、逐数组结果及适用限制见[新版S2结果](GPU_S2_B2_V2_RESULTS.md)。旧统一阈值下两组校准分别198/343和202/343数组超标的记录未覆盖。

## 5. S3：单区域、单输出，打通真实GPU闭环

**目的与依据：** R原文第3节路径和第8节G0；L先验证一个区域的一条依赖链，排除多区域/多token因素。

**条件：** S1/S2通过；K；主P、最多1输出；M1一个区域；新Session/H0；所有模拟计算段设为0，真实CUDA照常执行；verify模式。该零计算配置仅验证功能，不解释GPU性能。

**操作：**

1. 三路对照：独立CPU、同算子native、M1-HBF CUDA。HBF依赖通过同步桥等待所有子Global最终结果，再允许消费者继续。
2. 独立求交，验证未选区不提交、选区无漏交/重复、地址和content一致；检查父完成取子Global最终完成最大值。
3. 仅保留首次实际非EOS输出的token可交付时刻，或如实记录EOS/N=0；输出上限后无额外预测步。
4. 单独运行M8的8KiB回归（仍是单区域），以及公开故障入口的初始化持续program-fail和运行限额子例。M8源范围若未在S2被证明可表达，该子例阻断，不能用S1合成结果代替GPU回归；不宣称旧q_proj数值复现。

**产出：** 单区域 `numerical.json`、`coverage.csv`、桥/Global日志、`tokens.jsonl`、请求/初始化/排空记录，以及故障时消费者是否发射的证据。

**进入S4的标准：** 正向案例三方通过冻结数值合同，native/HBF相同CUDA路径关键数组精确一致；选区访问全部成功且最终排空。零计算下相对t0的token模拟时长等于此前HBF等待；N<2时TPOT=null。故障子例不得继续依赖计算，限额不得伪报成功/排空；故障结果不混入正向延迟。

**已执行结果（旧合同下诊断）：** M1的4KiB读对应1个Global，M8的8KiB读对应2个Global；零计算时token相对t0分别为217222ps、323910ps。两例各451个有效快照及完整logits与native逐位一致，访问成功且排空；初始化持续program-fail和运行时间限额均阻止依赖消费者继续，限额后未决项如实保留。原批次总状态blocked，因为当时B2未合格；新版B2通过不会自动改写原批次，三方数值须按新版重新核验。上述ps数值仅为未校准H0的零计算功能结果。详见[S3结果](GPU_S3_RESULTS.md)。

**新版合同重验：** `20261101-s3-b2-v2-001` 中native、M1、M8的CPU对照通过，GPU完整logits和有效快照一致；两个负例与排空检查通过，S3阶段pass。

## 6. S4：多区域、单输出，只扩大映射范围

**目的与依据：** R原文第5节的多区域、交集和覆盖要求。相较S3，正向主例只改变选区M1→M2，固定模型、P、输出上限1、CUDA执行方式、零计算及H0。

**操作：**

1. 新Session初始化M2两个区域，记录canonical storage、Global布局、content和padding。新区域填充不计有效权重。
2. 对所有原始回调独立求交；同回调若命中多个区域，串行服务且计算不重复推进。主P未自然触发跨区/别名时，使用S1对应合同子例验证，不声称模型自然使用了这些特殊关系。
3. 对M2-offset另跑非零偏移回归，其他条件相同。该范围较M2少64B，只验证偏移和覆盖正确，不把延迟差解释为等覆盖量优劣。

## 7. S5：多区域、多输出，验证token时间链

**目的与依据：** R原文第4/6/7/8节要求多token、每token尾段、EOS/失败处理。相较S4，先只改变输出长度，再单独改变功能测试的计算输入。

**条件与子例：** K、M2/H0不变；主P先执行最多2输出，再执行最多8输出，实际N按EOS处理。每个长度都建立对应事件序列，不把2输出的完整表冒充8输出的表。

| 子例 | 模拟计算条件 | 应检查的结果 |
|---|---|---|
| S5-a | 所有计算/传输段为0 | 每个token相对t0时刻仅由此前选区等待解释；每个ITL等于该区间等待 |

## 13. 失败后回到哪一步

| 发现的问题或变化 | 重新建立的依据 |
|---|---|
| 模型/权重转换/分词/主prompt改变 | S0身份；S2数值与事件；重做受影响S3—S5；S6新表 |
